**Author:** Yash Pathak

**Status:** Research complete. This report is the submission document for Phase 1. Literature review: 41 numbered papers, plus a Toyama footnote and a GhostyNav related-system note.

> **Vision, in one line:** Sit down at an ordinary Windows laptop, and use the whole computer — cursor, clicks, apps, typing, settings — by being watched by its webcam, with a live AR overlay on the screen showing what the system understands. No headset. No extra hardware. Stark-inspired, built as real engineering.

## Problem Statement

Today, using a computer still means touching it: a mouse, a keyboard, a trackpad. That leaves out real situations — hands busy, dirty, injured, or absent; limited mobility; presenting, cooking, repairing. The problem this project solves is: **can one ordinary laptop webcam, watching the user, give full control of a Windows computer, with an AR overlay on the screen that shows what the system sees and intends — running on a consumer CPU, with no headset, no depth sensor, and no extra hardware?**

Full control means, in one session:

- Move the cursor precisely to any target, large or small.
- Click, double-click, drag, and scroll.
- Launch any application, switch between windows, and manage files.
- Type into any application, including shortcuts (Ctrl+C, Alt+Tab) and passwords.
- Change system settings (volume, Wi-Fi, brightness, dark mode).
- Do all of this through an AR/HUD overlay that shows the current mode, the focused window, the pending action, and its confidence — and lets the user cancel with one gesture.

Constraints: one built-in laptop webcam; a consumer laptop CPU; arbitrary Windows applications — not one specially-built demo app; real rooms (changing light, glasses, other people in frame, long sessions).

Success looks like a working system, evaluated on a borrowed Windows task set (in the style of OSWorld / Windows Agent Arena) against a mouse-and-keyboard baseline, reporting task success, time, errors, false activations, CPU use, lighting robustness, and fatigue — plus a small public dataset of webcam-video + screen-state + OS-action traces, because none exists today.

## Existing Works — Literature Review

### How papers were found and chosen

Papers were found through web-index queries across seven areas: hand gesture / MediaPipe Hands; gaze, eye-tracking and head pose; AR overlays for desktop interaction; camera-based virtual keyboards and app control; multimodal control; accessibility camera control; and latency, robustness, fatigue and CPU-only performance. Queries also covered datasets (HaGRID, Jester, nvGesture, EgoGesture, SHREC, MPIIGaze, GazeCapture, ETH-XGaze, Gaze360), full-OS benchmarks (OSWorld, Windows Agent Arena), and the touchless expansion areas (mid-air gesture interaction, touchless/touch-free user interfaces, contactless computer control, gesture elicitation for touchless interaction, touchless UI frameworks and evaluations, fatigue and accuracy of mid-air interaction).

The shortlist was chosen by these rules:

- **Include first:** peer-reviewed work (CVPR / ICCV / ECCV / CHI / UIST / IEEE / ACM venues, or a widely adopted open system with a paper, e.g. MediaPipe Hands) that *demonstrates a control loop* — a cursor, a click, a typed character, a completed app/OS task — not classification accuracy alone.
- **Prefer:** a single RGB webcam (no depth sensor, Leap Motion, IR eye tracker or headset required), because that is this project's hardware constraint.
- **Exclude as filler:** generic "virtual mouse" student demos and blog posts with no user study, no dataset and no reproducible evaluation; depth-only gesture classifiers; commercial overlay products with no technical paper; and, for the touchless expansion, touchless payments, touchless fingerprint/biometric identification, and touchless sensing for non-interaction purposes.
- **Accuracy rule:** a number is quoted only when the paper reports it. Otherwise the table says **Not reported** — never an invented percentage.

**Framing — reviews and surveys (read before designing, not cited as results).** Groenewald et al. (2016) systematically reviewed 65 mid-air-gesture papers (gesture classification, domain, evaluation method) — its classification table is reusable for the vocabulary analysis, but it pre-dates webcam landmark tracking (MediaPipe era), so its technology conclusions are dated. Vogiatzidakis & Koutsabasis (2018) reviewed 47 elicitation studies (2011–2018) and found elicitation widely used but variable and ambiguous — the justification for running a standardised elicitation study and scoring it with Vatavu & Wobbrock's method. Koutsabasis & Vogiatzidakis (2019) systematically reviewed empirical (user-study) mid-air research, supporting the evaluation-gap claims (short sessions, lab settings, missing fatigue/longitudinal work). Rautaray & Agrawal (2015) surveyed vision-based hand-gesture recognition (segmentation → features → classification) — useful background for the recognition pipeline, but pre-deep-learning, so it is not cited for current accuracy or webcam-only performance.

#### (c) Gesture vocabulary design

This subsection directly feeds a new methodology step: run a small elicitation study for the OS-command vocabulary and score it with Vatavu & Wobbrock's agreement analysis — the methodology otherwise invents a vocabulary (pinch = confirm, palm = cancel) without evidence.

| Paper | Methodology | Advantages | Disadvantages | Accuracy |
|---|---|---|---|---|
| User-Defined Gestures for Surface Computing — Wobbrock, Morris & Wilson (2009, CHI) | Guessability/elicitation study: 20 participants shown effects (referents) and asked to invent gestures; proposals clustered, agreement scores computed; a user-defined, conflict-free gesture set + a taxonomy of surface gestures; elicited corpus of 1,080 gestures for 27 commands | The method to copy to derive a vocabulary (cursor/click/drag/scroll/launch) instead of inventing one: it measures what users already expect, and its agreement score is a defensible selection criterion. Foundational for all later elicitation work | Surface (touch) gestures, not mid-air — transfer to touchless must be argued, not assumed; elicitation shows preference, not recogniser performance; no live system evaluation | Not reported (agreement scores, not classifier accuracy) |
| User-Defined Gestures for Augmented Reality — Piumsomboon et al. (2013, CHI Extended Abstracts) | Wobbrock-style elicitation extended to AR: participants design gestures for AR tasks; consensus set built, rated for goodness and ease of performance; a published 44-gesture consensus set (34 unimanual, 10 bimanual) | The direct bridge from Wobbrock (surface) to mid-air/AR: a concrete starting vocabulary for a webcam system, with the caveat that AR headsets differ from a laptop screen | CHI Extended Abstract (short paper), AR-headset context, not desktop OS control; ratings are subjective, not recognition accuracy; gestures were elicited, not evaluated in a live recogniser | Not reported (goodness/ease ratings only, not recognition %) |
| Formalizing Agreement Analysis for Elicitation Studies: New Measures, Significance Test, and Toolkit — Vatavu & Wobbrock (2015, CHI) | Formalises elicitation analysis: new agreement measures, a significance test for agreement rates, and a toolkit — so agreement claims from studies like Wobbrock/Piumsomboon can be tested rather than eyeballed | Gives the project's own gesture-elicitation study a rigorous analysis method; prevents the common error of reporting raw agreement without a significance test. Method paper, so it ages well | No system, no gestures, no accuracy — pure method; applying it correctly requires a properly run elicitation study first | Not reported (method paper) |
| Understanding Mid-Air Hand Gestures: A Study of Human Preferences in Usage of Gesture Types for HCI — Aigner et al. (2012, Microsoft Research Technical Report) | 12 participants cooperating on 6 tasks using only hand gestures to communicate (human-to-human, no speech); 5,500 gestures coded with a novel classification combining three existing taxonomies (pointing, pantomimic, direct manipulation, semaphoric, iconic) | A gesture-type taxonomy for mid-air specifically — it tells the project which kinds of gestures users reach for for which meanings, rather than a flat list of poses; widely reused as the classification in later mid-air reviews | Technical report, not peer-reviewed — supporting only; human-to-human communication, not human-computer control, so the mapping to OS commands is indirect; no recogniser, no accuracy | Not reported |

**Supporting note — Ruiz, Li & Lank (2011), User-Defined Motion Gestures for Mobile Interaction (Proc. CHI 2011, pp. 197–206):** a guessability study eliciting device-motion gestures (moving the phone itself) for smartphone commands, methodologically in the Wobbrock family. Supporting-only: its input is moving the device, not freehand mid-air hand gestures.

#### (d) Interaction design foundations

| Paper | Methodology | Advantages | Disadvantages | Accuracy |
|---|---|---|---|---|
| Put-That-There — Bolt (1980, SIGGRAPH) | Speech + deictic gesture ("put that [point] there [point]") | The first proof that multimodality works when each channel does what it is good at — speech names the action, gesture names the target — rather than duplicating the same command in two channels | 1980 system, not a desktop OS controller; a division-of-labour lesson, not a complete system | Not reported |
| The Use of Eye Movements in Human-Computer Interaction Techniques — Jacob (1991, ACM Trans. Inf. Syst.) | Eye-tracker-driven techniques (object selection, scrolling, etc.) analysed as a dialogue; identified the Midas Touch problem | Foundational design lesson for any gaze system: eyes are always "on", so looking must not equal clicking; still the correct framing for a gaze+gesture hybrid | Used expensive 1990s eye trackers, not a webcam; qualitative/technique paper, no modern accuracy benchmark; dwell-time fix it popularised is slow | Not reported |
| 1€ Filter — Casiez, Roussel & Vogel (2012, CHI) | A speed-adaptive low-pass filter: strong smoothing at low speed (kills jitter), low lag at high speed | Directly reusable in a webcam cursor pipeline; two parameters, almost no CPU cost. Any webcam cursor that jitters without citing or implementing this (or a Kalman equivalent) has missed the obvious prior art | A filter, not a system — it stabilises a pointer, it does not decide actions | Not applicable (filter) |
| Gaze + Pinch Interaction in Virtual Reality — Pfeuffer et al. (2017, SUI) | Eyes select by visual indication; hands manipulate via pinch and other freehand gestures; targets at any distance without extra controllers | Solves the Midas Touch problem structurally (gaze selects, an explicit pinch confirms) — the cleanest design pattern for a webcam system combining gaze + hand input, avoiding dwell-time delays | Evaluated in VR with headset eye tracking, not a laptop webcam; evaluation was informal, so it provides no benchmark accuracy for a desktop system | Not reported |
| Typealike: Near-Keyboard Hand Postures for Expanded Laptop Interaction — Chhibber, Surale, Matulic & Vogel (2021, Proc. ACM Hum.-Comput. Interact. 5(ISS)) | A mirror reflector mounted on the built-in laptop camera redirects its view down to the hands/keyboard; 36 hand-posture variations trigger commands that would otherwise need keyboard shortcuts or mouse round-trips | Closest expansion match to 'single laptop webcam + shortcuts': runs on consumer laptop hardware, keeps hands at the keyboard, replaces shortcut/mouse round-trips | Requires a mirror attachment — not the unmodified front webcam alone; postures must be learned; misfires during normal typing are guarded by typing/non-typing classes | Over 97% classifying all 36 postures plus typing and non-typing classes; nearly 350,000 images from 30 participants, plus 20-participant real-time validation |
| Typing in Thin Air: The Canesta Projection Keyboard — Roeber, Bacus & Tomasi (2003, CHI Extended Abstracts) | A keyboard image projected onto any flat surface; an infrared light plane just above the surface is interrupted by fingers, a sensor detects the intersection, and software converts the data into mouse and keyboard events | Typing into arbitrary applications via generated keyboard events — the same output channel a desktop webcam-typing system needs; no physical keyboard required | Needs projection + IR hardware (not a laptop webcam alone); touch typists reported lower satisfaction and higher error rates | Not reported |
| CamK — Yin et al. (2016, IEEE INFOCOM) | Camera watches typing on a printed paper keyboard; keystroke localisation and false-positive rates reported | The strongest peer-reviewed camera-typing result found | Needs a printed layout and a phone camera angle, so it does not solve on-screen desktop typing | Over 95% keystroke localisation, 4.8% false-positive keystrokes, 1.25× typing speedup vs on-screen keyboard for regular text |

#### (e) Fatigue, privacy and risk

| Paper | Methodology | Advantages | Disadvantages | Accuracy |
|---|---|---|---|---|
| Consumed Endurance — Hincapié-Ramos et al. (2014, CHI) | Biomechanical + subjective model of shoulder/arm fatigue ("gorilla arm") for mid-air selection; compares click, dwell, swipe, second-hand methods | The only shortlist paper that quantifies why always-raised-hand control fails over time; directly constrains gesture design (rest poses, small planes, low-movement confirmation) | Mid-air large-display setting, not laptop-desk; small lab sample; a metric, not a complete system — it tells you what to avoid, not how to build the controller | Not reported as accuracy; fatigue result: click lowest consumed endurance (8.18%) and lowest Borg CR10 (1.19); swipe worst |
| Modeling Cumulative Arm Fatigue in Mid-Air Interaction — Jang et al. | PrivacyLens: On-Device PII Removal from RGB Images using Thermally-Enhanced Sensing — Iravantchi et al. | Bystander Privacy in Smart Homes: A Systematic Review — Saqib et al. (2025, ACM Trans. Comput.-Hum. Interact.) | Systematic review of bystander privacy: people with no say in deployment/configuration yet exposed to data collection (guests, tenants, domestic workers) | Gives the review a principled privacy framing beyond the primary user: an always-on laptop camera also captures bystanders; tangible controls/indicators (lens shutters, visual/auditory indicators) translate into design requirements | A review, not a system evaluation — it does not test a webcam-control system and offers no accuracy figure | Not applicable (review) |
| Towards a General Video-based Keystroke Inference Attack — Yang et al. (2023, USENIX Security) | Attack system needing only a single commodity RGB camera with a frontal view of typing fingers; no pretraining, no keyboard knowledge, no training data from the target | Essential risk evidence for camera typing, including passwords: camera-visible typing is itself a leakage channel, so a benign typing system must be designed against it (on-device processing, no recording, shielded typing, non-visual confirmation for passwords) | An attack paper, not a benign typing system — its camera geometry (frontal view of fingers) differs from a laptop webcam's view of its own user | Not reported |

### Related systems (not papers — practical context)

- **GhostyNav (TheCidSama/GhostyNav, GitHub, MIT).** A Dynamic Island-style notch overlay for Windows 10/11 (WPF/.NET) with a pixel-ghost voice assistant, control centre, widgets, stats, clipboard history and app launcher, in ~24 MB of RAM. Related system only, not peer-reviewed evidence. Its value here is as a practical reference for Windows overlay mechanics (top-most, non-activating, glanceable) — and as a warning: its "stealth" framing is an academic-integrity liability a university project must explicitly distance itself from.
- **Notch — Dynamic Island for Windows 11 (Jaswanth1902/Notch, GitHub).** An open-source, top-of-screen ambient HUD (60 fps spring physics, claimed under 40 MB RAM, zero focus theft) surfacing background-agent telemetry from JSON spool files. Closest honest analogue to a notch HUD: a small, non-activating, always-visible strip reporting system state without taking focus. This project's HUD copies Notch's constraints (no focus theft, tiny CPU/RAM, glanceable state) and replaces agent telemetry with controller state (mode, tracked hand/face, pending action, confidence).
- **Unhindered and Hands-Free Control.** Current accessibility products that already do much of this mission from a webcam: head → pointer, face/hand/voice → click, type, scroll, on-screen keyboard, fully offline (Hands-Free Control claims ~16 ms head tracking). Implication: this project cannot claim novelty for "webcam moves the mouse" — it must beat or differentiate on full-OS task coverage, evaluation, fatigue, privacy, or the AR HUD, and should benchmark against one of these (or eViacam/Camera Mouse) rather than only against a physical mouse.
- **eViacam / Enable Viacam (open source, Windows/Linux, GPL).** Head-movement mouse emulator with dwell/gesture clicking and an on-screen control bar; long-lived accessibility software, still the most credible free baseline for head-pose control.
- **Ghosty AI (ghosty-ai.com).** A Windows screen overlay that screenshots, transcribes audio and drafts answers, marketed as "stealth"/invisible to screen sharing, with hotkeys and automated typing. It proves Windows overlay mechanics are productised — but it is an AI answer assistant, not a camera controller, and its stealth framing raises academic-integrity questions a student project should explicitly distance itself from.

## Gaps and how our model fills them

| Gap | Source | How our model addresses it |
|---|---|---|
| Single-app demos vs full OS control | Camera Mouse (pointer only), WebGazer (gaze only), MediaPipe Hands (tracking only); OSWorld / Windows Agent Arena formalise OS tasks for agents, not camera users | A unified gesture+gaze+voice state machine with an explicit lock, confirm and cancel path, evaluated on a borrowed OSWorld/WAA-style Windows task set against a mouse baseline |
| Consumer-CPU real-time performance, honestly measured | MediaPipe Hands (phone-GPU times only); virtual-mouse write-ups with no end-to-end latency budget | An end-to-end latency budget (capture → inference → smoothing → OS injection → screen feedback) with CPU-% and frame-drop reported at 720p with face + hands + gaze running together |
| Robustness to real rooms and lighting | MPIIGaze, Gaze360 (wild gaze data); HaGRID, Jester (cluttered gesture data); control papers rarely report a lighting × occlusion × distance matrix | A lighting/occlusion/distance robustness matrix in the evaluation, and a trace dataset collected across bright, evening and backlit conditions |
| Multi-person scenes and attention ownership | No shortlist system addresses "which person is the user?" (identity persistence, face/hand association, lock/unlock) | Face/hand association across frames, a deliberate lock/unlock gesture, and context gating (gaze direction, face/hand association) that suppresses firing on bystanders; a second-person-in-frame test split |
| Fatigue over long use | Consumed Endurance (metric, not longitudinal); Jang (cumulative-fatigue model); camera-control evaluations typically minutes long | A rest-pose, low-fatigue vocabulary (hand on desk, micro-gestures + head/gaze for pointing, pinch only to confirm); Borg rating + error rise over session length; cumulative-fatigue-driven rest prompts |
| The Midas Touch + confirmation problem, unsolved in practice | Jacob (1991); dwell, pinch, blink and voice confirmations that themselves misfire; no measured false-activation rate for a complete desktop system | Gaze never clicks alone; every consequential action passes through a visible PENDING state with confidence and a one-gesture undo; dwell vs pinch vs voice confirmation compared on the same tasks |
| Typing is the weakest link | Camera Mouse / eViacam (slow dwell/on-screen keyboards); CamK (printed-paper keyboard); voice dictation fails for passwords, code, shortcuts and noisy rooms | Typing and shortcuts through the OS action layer into arbitrary apps, with shielded, non-visual confirmation for passwords and on-device processing (Yang et al. as risk evidence) |
| Privacy of an always-on camera | Control papers rarely discuss it; Saqib (bystanders); PrivacyLens (on-device removal) | On-device processing only; no video storage by default; visible on/off + lock gesture; landmark-only logs unless a participant consents to video; bystanders not recorded as subjects |
| Evaluation comparability | Gesture papers use different vocabularies, splits, lighting and metrics; gaze papers use cm, degrees and pixels interchangeably | A shared task set, a shared negative class ("doing other things", Jester's lesson), and a shared reporting template (success, time, errors, false activations, CPU, lighting) against a mouse/keyboard baseline |
| AR overlay as interaction, not decoration | WindowSpace (overlay/window management as a research problem); flat-screen HUD work mostly cosmetic | A confidence-aware HUD (mode, focused window, pending action + confidence, cancel affordance, magnified gaze target) evaluated HUD-on vs HUD-off, built as a top-most, transparent, non-activating window |
| Vocabulary without evidence | Wobbrock, Piumsomboon (elicitation method exists); Vatavu & Wobbrock (agreement analysis); Gentile (configuration choices change performance); no OS-command vocabulary derived from users | A vocabulary-derivation step before the state machine: an elicitation study (n≈15–20, OS referents) scored with Vatavu & Wobbrock agreement analysis; the consensus set is what the state machine implements |
| False activation measured in real use | Jacob et al. (2013, context cues) and Charade (1993, active zone) — the sterile-touchless literature is the only place false activation is measured in real use | An explicit active state (lock gesture / active zone) plus a confirmation channel, with context gating suppressing bystander firing; false activations per session as a headline metric |
| Touchless UI configuration (representation + activation) | Gentile et al. (2023) — the first cited paper varying avatar/activation/layout and measuring the effect | The HUD-on/off experiment tests the same hypothesis on this system: an activation gesture plus a visible representation vs none |

## Innovations in our model

1. **Unified gesture+gaze+voice state machine.** An explicit lock, confirm and cancel path (LOCKED → POINTING → PENDING → CONFIRMED → ACTING → UNDO-AVAILABLE), a vocabulary derived from an elicitation study rather than invented, and context gating against bystander firing — evaluated on a borrowed OSWorld/WAA-style Windows task set with a mouse baseline.
2. **Rest-pose, low-fatigue vocabulary.** The hand rests on the desk; pointing uses small movements + head/gaze; the arm is never required to stay raised; pinch is used only to confirm.
3. **Confidence-aware AR HUD.** The overlay shows what the system thinks you meant before it acts (mode, focused window, pending action + confidence), with a one-gesture undo.
4. **On-device-only processing with a kill switch.** No video leaves the laptop by default; landmark-only logs unless a participant consents to video; a visible enabled/disabled indicator and a software kill switch (key + both-palms pose); the system starts DISABLED.
5. **A small, consented, public webcam-OS-control trace dataset + reporting template.** Webcam video (consented) or landmarks, screen state, OS actions, success, time, errors, false activations, CPU use and fatigue ratings — so the next student can compare.

## Usage and benefits

| Area | Use |
|---|---|
| Everyday computing | Touch-free control of the whole computer — cursor, clicks, apps, typing, settings — from the laptop webcam, with no extra hardware |
| Accessibility | Camera control for people with limited mobility, for whom a camera is far easier than a mouse |
| Hands-busy work | Presenters, makers, cooks and technicians who cannot keep returning to the keyboard |

Benefits: no headset, no depth sensor and no extra hardware — one built-in webcam on a consumer laptop; full OS control in one session; on-device processing with landmark-only logs; an AR overlay that shows what the system intends before it acts.

## Methodology: start to end

| Stage | Method | Output |
|---|---|---|
| Vocabulary derivation | Elicitation study (n≈15–20) for OS referents (point, click, double-click, drag, scroll, launch, switch, type-confirm, cancel, lock), scored with Vatavu & Wobbrock agreement analysis; the consensus set is implemented | OS-command gesture vocabulary |
| Capture | One laptop webcam (720p target) + microphone (voice optional, not required); frames + audio timestamped | Frames + audio, with capture latency counted in the end-to-end number |
| Perception | MediaPipe Hands (21 landmarks, 2.5D); appearance-based gaze (WebGazer-style ridge regression for the browser layer, MPIIGaze/GazeCapture-pretrained model for the native layer); head pose from face landmarks; all on-device, CPU-targeted | Landmarks + gaze point + head pose per frame, with confidence |
| Fusion + smoothing | 1€ filter for cursor stability; short temporal window for dynamic gestures with explicit background / "no gesture" handling (Jester's negative classes); Kalman-style fallback | Stable, low-jitter pointer + gesture/gaze event stream that does not fire on noise |
| Intent state machine | LOCKED → POINTING → PENDING → CONFIRMED → ACTING → UNDO-AVAILABLE; gaze/head points, voice names the action, pinch confirms, open-palm cancels, lock gesture locks/unlocks; context gating (an explicit active state plus a confirmation channel; face/hand association and gaze direction suppress firing on bystanders); rest-pose design | Confirmed actions with visible confidence + one-gesture undo |
| OS action layer | Native Windows input injection: cursor move, click, drag, scroll, app launch/switch (including Alt+Tab), typing (including shortcuts), settings toggles; software kill switch (key + both-palms pose); visible enabled/disabled indicator; starts DISABLED; actions clamped, drags release if tracking is lost | Real Windows input, safely gated |
| AR HUD overlay | Top-most, transparent, non-activating overlay (mode, tracked hand/face status, focused window, pending action + confidence, cancel affordance, magnified target for gaze pointing); evaluated HUD-on vs HUD-off | Glanceable controller state + a measured answer to whether the overlay helps |

**Evaluation.** Task set: 15–25 Windows tasks borrowed from the OSWorld / Windows Agent Arena taxonomy (file, browser, office, settings, multi-app), run by human users through the camera system and through mouse/keyboard. Metrics, reported together: task success, completion time, errors, false activations per session, CPU use + frame drops, lighting/occlusion/distance robustness matrix, and fatigue (Borg rating + error rise over session length). Comparisons: mouse/keyboard baseline; eViacam/Camera Mouse baseline; HUD-on vs HUD-off; dwell vs pinch vs voice confirmation. Splits: held-out users; varied lighting; a second person briefly in frame. Honesty rules: accuracy is reported only where measured; agent benchmark scores are never presented as human baselines.

**New dataset.** Because no webcam-video + screen-state + OS-action trace dataset exists for full desktop control, this project collects one: 15–25 scripted Windows tasks × several users × varied lighting (bright, evening, backlit) and conditions (glasses, second person briefly in frame), recording landmarks, recognised gestures, OS actions, success, time, errors, false activations, CPU use and fatigue ratings — consented, on-device, landmark-only by default.

## Datasets

| Dataset / benchmark | Size & content | Best use for this project |
| --- | --- | --- |
| HaGRID (Kapitanov et al., WACV 2024) | 554,800 FullHD images, 18 gestures + "no gesture", 37,583 subjects, 0.5–4 m, varied natural light, bounding boxes | Static-gesture pretraining / validation for a device-control vocabulary |
| HaGRIDv2 (2024/2025) | 1,086,158 images, 33+1 classes, 65,977 subjects, boxes + keypoints | Same, with a larger vocabulary and dynamic-gesture support |
| 20BN-Jester (Materzynska et al., 2019) | 148,092 webcam videos, 27 classes (25 gestures + "no gesture" + "doing other things"), 1,376 actors, ~3 s clips; split 118,562 / 14,787 / 14,743 | Dynamic-gesture training; its two "negative" classes are the right way to teach a live system not to fire |
| nvGesture (Molchanov et al., 2016) | 1,532 RGB-depth videos, 20 subjects, 25 classes, car interior, dim/bright light | Dynamic-gesture baseline; contrast case showing what depth buys (and what a webcam-only system gives up) |
| EgoGesture (Zhang et al., ICCV 2017 lineage) | 2,081 RGB-D videos, 24,161 gesture samples, 2,953,224 frames, 50 subjects, 83 classes, 6 indoor/outdoor scenes incl. walking + drastic sunlight | Continuous-gesture detection (segmented + unsegmented testbed) |
| SHREC / DHG-14/28 (2017) | 2,800 depth+pose sequences, 28 subjects, 14 or 28 classes | Skeleton-based dynamic gesture comparison |
| MPIIGaze (2015) | 213,659 images, 15 laptop users, everyday use over 3+ months | Laptop-gaze fine-tuning / in-the-wild robustness test |
| GazeCapture (Krafka et al., 2016) | ~2.5M frames, over 1,450 people, phone/tablet front cameras, varied backgrounds/poses/light | Large-scale gaze pretraining; held-out-user evaluation |
| ETH-XGaze (2020) | Over 1M high-resolution images, 110 participants, 18 DSLR cameras, extreme head pose/gaze, standard protocol | Head-pose robustness benchmark; pretraining reference |
| Gaze360 (Kellnhofer et al., 2019) | 238 subjects, indoor+outdoor, 129k train / 17k val / 26k test images, 1–3 m camera distance, full yaw range | Unconstrained gaze evaluation (distance + pose variation) |
| RT-GENE (Fischer et al., ECCV 2018) | ~92k images, 13 subjects (as summarised in later papers), 80–280 cm distance, raw + normalised versions | Gaze at a distance (closer to a desk than phone datasets, farther than a webcam's ideal) |
| EyeDiap (2014) | Video from 16 subjects, screen-target + floating-target sessions, RGB-D (Kinect) | Screen-target gaze (the desktop-relevant subset) |
| OSWorld (2024) | 369 real OS tasks, Ubuntu/Windows/macOS, setup + execution-based evaluation scripts | Task taxonomy + scoring template for this project's own human-input evaluation (do not reuse its agent scores) |
| Windows Agent Arena (2024/2025) | 150+ Windows tasks across 11 apps, PyAutoGUI-style action space (click, drag, scroll, type, hotkey) | Windows task checklist + action vocabulary for this project's test suite |

**Flag — no standard benchmark exists for full OS-level control by webcam input.** OSWorld and Windows Agent Arena are the closest benchmarks, but both score autonomous agents acting on screenshots, not humans acting through a camera. There is no published dataset of webcam video + screen state + OS action traces for full desktop control, and no agreed metric that jointly scores task success, time, errors, fatigue and robustness (lighting, occlusion, second person in frame). A project that creates even a small version of this — e.g. 15–25 scripted Windows tasks × several users × varied lighting, with video, landmarks, actions and success/time/error logs — would itself be a contribution, provided consent and on-device handling are documented.

## Vision

Morning. You sit down at your laptop. The webcam wakes — nothing to wear, nothing to plug in. You raise a hand, and the screen answers: a calm overlay shows it sees you, shows the window you are looking at, and waits for you to mean something. You point at Spotify; a pinch opens it. You glance at the volume; a small hand movement turns it down. You circle an error message and ask what it means. You never touch the mouse — not because the mouse is gone, but because, for this task, you did not need it. When you are done, one gesture locks the camera off, and the laptop is just a laptop again. That is the whole ambition: the computer paying attention the way a good assistant does — visibly, confirmably, and only when you want it.
